## Mechanism and enumeration

**The shared assumption:** the rows that `FWA_Downstream()` returns, cut to main flow and sorted `wscode DESC, drm DESC, id DESC`, are a geometrically contiguous chain from the origin, and a row's `waterbody_key` / `edge_type` say where the walk is relative to a bank. FWA's local codes break that in two ways: a confluence that the local code places somewhere other than where the lines meet, and a row whose local code is out of step with its measure (`FWA_Downstream()` then drops a row on the true path, or admits a row that is not on it). Each earlier fix papered over one consequence of this: NULL local code (round 1), a jump across dry land (round 2), the re-entry, mid-row entry and same-line guard (author).

Every place it reaches, with evidence. "BULK" means a scratch copy built for this review: `frs_network_segment()` on BULK, plus wet's annual-pick discharge as the check script does. It was built in `zz_review3_nr` and dropped afterwards. q = 3, d = 1,000 m.

1. **Path order across more than two lines.** Handled. Every row that `FWA_Downstream()` returns has a wscode that is an ancestor of the origin's, or equal to it, so `wscode DESC` orders the lines by depth. The other case is the same-wscode "missed side channels" branch, where two main-flow lines would interleave by measure. In BULK no wscode is shared by two main-flow lines with a local code (0). Province-wide there are 2 real cases (BEAV `200.692231.387879`, SIML `300.432687.380566.173428`) plus the `999…` placeholder code. `999` lines walk only their own line, because every `FWA_Downstream()` branch is false between equal 999 codes.
2. **`LAG(prev_pt)` across a jump, and `below_m` from a far point.** This is only a lower bound. Each piece of `path_m` is a walk along a line or a straight jump, so `path_m` is at least the straight distance from the origin, and it is never negative. Where the local code places a confluence *below* the point where the lines meet, though, fresh jumps straight to the first row returned and skips the stretch of the parent line between the two points. The committed log shows this: in `data-raw/logs/near_river_259/bulk_compare.csv`, 6 `entry` segments have a centreline distance *shorter* than the reference's, by 14 to 67 m (`centre_diff_m < 0`). Example: 17059193. Its first path row (17058605) is 101 m away. That row's top, at measure 150.8, is where the local code puts the confluence, while the nearest point on the line is about 40 m away near measure 285. Fresh gives 252 m, the reference 285 m. See finding 2.
3. **Rows that `FWA_Downstream()` drops from the true path** (local code equal to or above the origin's). Handled conservatively, and in some cases correctly by accident. Example: Bulkley row 17014753 at measure 28,696.7 has local code `…103213`, out of step with the rows above it (`…103108`). The walk jumps over it in a straight line. When that jump lies inside the target's polygon, its in-polygon part is subtracted. 283 of 1,043 subtracted jumps start inside the landing polygon, and not subtracting them would change the winning distance for 124 origins. I checked the two origins that would cross 1 km, 17063864 and 17063867 (951.6 vs 1,025.2 m). There the jump replaces Bulkley rows (≥ q) that `FWA_Downstream()` dropped because their local code equals the tributary's, so the subtraction lands exactly on the bank. The subtraction is right.
4. **The prefilter (`ST_DWithin` at `cap`) removing rows before the windows.** Handled. A row more than `cap` from the origin's geometry can be passed only at `path_m > cap`, because `path_m` is at least the straight distance. Every later row is then past `cap` and filtered out, so a dropped row cannot shorten a kept one. Measured: `frs_near_river(q = 3, d = 1000)` alone and `c(3, 8)` with `c(1000, 15000)` agree on all 2,118 segments within 1 km at q = 3 (0 differ either way).
5. **Connector rows on the path: inside their polygon, and wholly?** Handled for BULK. 1,603 main-flow 1400s, 1,050 main-flow 1450s and 574 side-line 1450s all have a polygon with their `waterbody_key`, and none lies more than 1 m outside it (sum outside: 0 m). Main-flow 1400s are all order 1 or 2 (mostly wetlands), so treating them as non-targets loses no river.
6. **A `waterbody_key` that recurs in separate runs along a path** (wetland 1050 lines weave in and out; BULK has 331 line/key pairs with more than one run). A subtraction from an earlier run could reach a target in a later run. Measured, it moves no answer: computing the subtraction per contiguous run instead gives the same winning distance for every origin (0 differ, max difference 0).
7. **Several jumps into one polygon, and the `cap` allowance.** Not guaranteed. See finding 1.
8. **The correlated polygon subquery's column binding.** Correct. `entered` selects `FROM downstream` with no alias, so `downstream.prev_pt` and `downstream.geom` bind to the current row. `p.geom` and `p.waterbody_key` are the polygon's, and the outer `CASE` columns are unqualified with only `downstream` in scope. Polygons that share a key never overlap (195 multi-polygon keys on BULK, 0 overlapping by more than 1 m²), so `sum()` cannot count one area twice. `entry_in_m` was never larger than `jump_m` (0 rows).
9. **The `capped` filter on `path_m` before the subtraction.** This is what finding 1 depends on. A target needs `path_m = bank + connector_m <= cap`, which holds only while `connector_m <= conn_max`.
10. **`dist_m >= 0`.** Holds. 0 non-connector rows have `path_m - connector_m < -1e-6` (min −3.8e-11). The 1,363 negatives are connector rows, whose own `below_m` is in `connector_m` but not in `path_m`. They are never targets.
11. **Invariants outside the walk.** All hold. Rules without `near_river` compile as before, because the size parts are still appended last. The EXISTS reads only `s.id_segment` and `s.watershed_group_code`. `.frs_near_river_specs()` and the predicates read the same `params[[sp]]` object, and `discharge_min` goes through `.frs_sql_num()` on both sides. Origins need a local code, and each spec's rows require `origin_mad IS NULL OR < q`.

## Findings

- **[severity: fragile]** R/frs_near_river.R:133-147 and :292-294 (`conn_max = on_path + side`, `least(entry_max, …)` per jump), with the `capped` filter at :355-356. The comment at :293-294 says capping each jump at `entry_max` keeps the cap and prefilter (`max(distance_max) + conn_max`) sufficient. That assumes a path subtracts at most one entry and one connector run per polygon. It does not: `connector_m` sums `entry_in_m` over **every** jump that lands in the polygon. On BULK, 78 (origin, polygon) pairs have two subtracted jumps, and their entries sum to as much as 519 m against `entry_max` 411.7 m. Example: origin 17014634 jumps 430.8 m into polygon 329706585, subtracting 281.4 m, then jumps 237.6 m over the out-of-step row 17014753, subtracting another 237.6 m. When `connector_m` exceeds `conn_max`, a target with `path_m - connector_m <= distance_max` can have `path_m > cap`. `capped` (and possibly `ST_DWithin`) then drops it, the segment loses its row, and whether it is dropped depends on the largest `distance_max` among *other* specs in the call. That breaks the invariant that one spec's answer is independent of the others. It does not occur on BULK: the largest `connector_m` is 2,983 m against `conn_max` 3,395 m, and the spec-independence check above shows 0 differences. A group with a long on-path connector run and a second entry into the same polygon would be enough. One direction for a fix: cap each origin's total `entry_in_m` per polygon at `entry_max` (one bank crossing per polygon), or derive the allowance from a bound the SQL enforces rather than from the table's longest single run.
- **[severity: fragile]** R/frs_near_river.R:324-325, :341-343 (`prev_pt`, `jump_m`, `below_m`). Where a local code places a confluence below the point where the tributary meets its parent, fresh reads **shorter** than a nearest-point walk that counts no gap. The tradeoff accepted for this review ("entry-point differences make fresh LONGER"), and the invariant that `dist_m` is never shorter than the true network distance, both assume otherwise. Measured in the committed log `data-raw/logs/near_river_259/bulk_compare.csv`: 6 `entry` segments have `centre_diff_m` from −14.3 to −67.1 m (17074299, 17059193, 17070827, 17073783, 17072620, 17011825). 17059193 is traced in item 2 above. The shortfall is bounded by the length of the skipped stretch minus the straight jump, and it can grow on a meander. No segment changes at 1 km on BULK. The check script's `entry` class absorbs these residuals in both directions, so nothing has flagged them. Either state that the bound runs both ways, or measure the jump to where the tributary geometrically meets the parent line rather than to the first row returned.
