## Findings

- **[severity: fragile]** R/frs_watershed_at_measure.R:149-150 and 159-164 (new `.frs_watershed_simplified()`). `blue_line_key` and `up_blk` go into the SQL through `sprintf("%s", <double>)`, which R writes in scientific notation when that is shorter: `sprintf("%s", 356000000)` is `"3.56e+08"`. Postgres reads that as `numeric`, and `fwa_watershedatmeasure(integer, double precision)` does not resolve. I measured it on a real FWA key: `blue_line_key = 356000000` (LNTH) exists, and `frs_watershed_at_measure(conn, 356000000, 5000, simplify_m = 25)` fails with `function whse_basemapping.fwa_watershedatmeasure(numeric, integer) does not exist`. The `simplify_m = NULL` path fails the same way (lines 103-104, 116-117). So this is a pre-existing defect, and the new query copies it. The brief says the blk and measure interpolation is acceptable because both are "validated numeric", but numeric validation does not prevent this failure. It applies to any double key whose scientific form is shorter than its fixed form (six or more trailing zeros on a 9-digit key; integer input is unaffected). The fix belongs in both paths: `%d` with `as.integer()` for the keys, as `.frs_resolve_aoi()` already does for `list(blk, measure)`, and `.frs_sql_num()` for the measures. Report it or file an issue rather than fixing only the new path. Only one key in the current FWA table is affected, so I rate it fragile, not a bug.
  - **Rule:** code-check-r.md "`sprintf("%g", x)` writes `Inf` and `NA` into SQL as bare words, which Postgres reads as column names" (a numeric formatter with no SQL form for some values; here the format is `%s`)
